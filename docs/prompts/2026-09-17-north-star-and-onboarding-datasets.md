Matthew: *"screenshots could have a lot of data because i can just cross over a full section of that
page if i dont like it so make sure it actually reads what we are sending."*

- There is already a screenshot reader: `src/lib/clients/screenshot-read.ts`. **It transcribes the

  reached only from the presence sweep.

  (`skin-vision.ts`, `review-read.ts`, `listing-read.ts` and others). The capability is there.
- Build a **page-annotation reader**: given a screenshot of a drafted page with sections struck
  through, circled or arrowed, return a structured edit list against the page's `outline` headings.
- ‼️ **It must return references to the page's OWN sections, never free text.** A reader that returns
  "delete the pricing part" has moved the ambiguity downstream. It resolves each mark to an outline
  heading id, and an unresolvable mark is reported as unresolved rather than guessed, which is the same
  tri-state rule `screenshot-read.ts` and `mx.ts` already carry.
- ‼️ **A read is a PROPOSAL.** It posts the edit list and waits. Nothing applies an edit to a page from
  a picture without somebody confirming. The undo stack in `page-studio.ts` is the safety net and it
  only helps if the edit went through a path that pushes onto it.

## W8. The North Star: one labelled model of the whole strategy

Matthew: *"create a north star framework so all of the data of the offer, avatar, content, stages of
awareness, lead magnets, funnels, workflows etc ALL of it, labeled and stored correctly ... and make a
mind map with all of the outbound strategies labeled by keywords and pillars with the data of the views
in each one."*

**‼️ Take the name from the codebase, not from a whiteboard.** "North star" already means something
here: the one belief the prospect must hold before the offer is presented
(`avatar-framework.ts:251`, `verticals.ts:174` calls it *"the hinge / north-star belief"*). Build the
framework AROUND that meaning. A second, unrelated "north star" would be two things with one name.

**The model, and every node already has a table:**

```
client
 └── audience (client_audiences)          who buys, and in what words
      └── avatar (avatar_briefs)          shared research, voc quotes, approved numbers
      └── offer (client_offers)           what is sold, its outcome, price, guarantee
           └── north star belief          audience_documents kind=necessary_beliefs   ← EMPTY TODAY
           └── awareness ladder           audience_documents kind=awareness_ladder
                └── rung (1..5)           reader state, angle, claim, risk reversal
                     └── keyword          client_keywords, awareness_stage, role pillar|support
                          └── page        page_plan → client_pages
                               ├── angle       page_angles (idea, narrative, indoctrination)
                               ├── headline    client_headlines
                               ├── magnet      page_magnet_candidates → lead_magnets
                               └── evidence    page_sources
```

**Build:**

1. **A read model**, `northStar(clientId)`, returning that tree with every node marked present, missing
   or stale, and a completeness number per branch. This is W1's readiness gate seen from the top.
2. **The mind map.** Render the tree as a page under `/dashboard/clients/<id>/strategy`, grouped by
   pillar and keyword. Mermaid renders natively in artifacts and the repo already ships diagrams; a
   static SVG is fine. **What matters is that it is generated from the tables, never hand-maintained.**
3. **The view data, and be honest about it.** Matthew wants view counts per keyword and pillar.
   ‼️ **`weekly-report.ts` carries `ATTRIBUTION_NOT_WIRED` and tells the client in writing that nothing
   measures whether a published page was ever cited.** `page-dataset.ts` refuses ranking and citation
   columns for exactly this reason: *"a column no process can fill would put an invented number into
   the training set, which is worse than an absent one because a later reader cannot tell it was never
   measured."* So either wire a real source (Search Console is in the access step, GBP insights, the
   audit engine's own citation capture) or render the node with "not measured" on it. **Do not put a
   number on that map that nothing produced.**
4. **Labels are the point.** Every node carries its vertical, avatar slug, awareness stage and pillar
   so the map can be filtered to "everything we are doing for this avatar at this stage", which is the
   question the strategy is actually asked.

## Gotchas that have bitten before

- One unknown column fails the WHOLE PostgREST select, and supabase-js RETURNS the error rather than
  throwing, so a try/catch never fires. Read a new column in its own select.
- An embed between two tables with TWO foreign keys between them must name the constraint
  (`page_plan!page_angles_plan_id_fkey`). An unnamed one errors, and a swallowed error looks identical
  to no data.
- Postgres aborts a whole transaction on the first error, so a second "this is refused" assertion in
  one transaction catches "transaction is aborted" and passes for the wrong reason. Savepoint per
  expected failure.
- `NEXT_PUBLIC_APP_URL` is `http://localhost:3000` locally. **Never run a step generator locally**: it
  posts localhost links into production Slack.
- `slackFetch` returns `{ok:false}` and never throws. Check the body, never the promise.
- A card body over 3,000 characters fails the whole message. Everything goes through `bodySections()`.
- Resolve SRT by slug `srt-agency-llc`, never a pinned id.
- Never an em dash in copy or in anything a model writes.
- Paste full SQL in a fenced sql block, never a file path.
- Ask before deleting production data.
