Merged to `main` at `a51a83a` (12 commits). All five migrations are applied to production.

Ordered so that **what breaks first is tested first**. If step 1 is red, nothing below it means
anything: a red Vercel build serves the OLD code and every test below silently passes or fails
against last week's deploy. That is the failure mode `reference_vercel_stale_prod_build` records.

## ‼️ Two things that will look like bugs and are not

**1. Approve refuses on the Day 0 wall, for every client, right now.**
Measured 2026-09-22: `srt-agency-llc` has `day_0_archived_at` NULL, and so does every other client.
The Day 0 wall runs BEFORE the quality gate on purpose, so you will see
*"Day 0 is not archived, so publishing will refuse"* and never reach the compliance checks. That is
the wall working. Tick the Day 0 archive step on the board first, or waive it there with a reason.

`page_dataset` has **0 rows** in production. The learning half is wired and correct and has nothing
to read until pages actually flow through the studio. "0 verticals, posted false" is the right
answer, not a failure. It starts producing after you publish a page or two (section 6).

## 5. The compliance gate and the Approve button, end to end

**Prerequisite:** tick the **Day 0 archive** step on the client's board, or the wall refuses first.
See the warning at the top.

In `#aeo-seo-page-drafting`:

1. `page srt-agency-llc` at the channel top level. Expect a numbered candidate card.
2. A bare digit, e.g. `3`, to claim one.
3. Dictate or `draft` a body.
4. `check`

**What is new on that card:** the verdict now carries four more checks from the SAME model call:
`experience_claims` (block tier), `people_first`, `authority`, `spam_signals` (all warn), and an
**":white_check_mark: Approve and publish"** button under it.

5. Press **Approve and publish**.
   - Day 0 not ticked → *"Day 0 is not archived"*. Expected. Go tick it.
   - Gate passed → *"Approved by @you and published"* plus the live URL.

**Test the block path.** Put a credential claim no source carries into the body, e.g.
*"Our surgeons have twenty years of experience and are board certified."* Then `check`.
Expect `experience_claims` to **fail at block tier** and the verdict to read `:no_entry: Blocked`.

6. Press Approve anyway. Expect a refusal naming the reason, and a line offering the waiver.
7. Type the waiver with a real reason (it must be 10+ characters):

```
waive: the board certification is listed on their state licence page
```

Expect *"Waived and recorded"* and a post to `#alerts-infra`. It does **not** publish.
8. Press **Approve and publish** again. Now it publishes.

**Test the staleness fix (this is the new `meta_hash` half).**
- `check` a page, then change its **title** on the board, then press Approve.
- Expect a refusal: *"The title, meta description or slug changed after the page was checked."*
- Before today that edit went undetected and the page would have published on a stale verdict.

**Test that Approve is a confirmation and not a bypass.** `check`, then `add: one more sentence`,
then press Approve. Expect *"The page changed after it was checked"*.

## 8. The cron passengers

Both weekly jobs ride `/api/cron/followup-digest` and gate on **Thursday** inside the module, so on
any other day they return `skipped: "weekday"` without a single HTTP request.

Dry run against production (add the `Authorization: Bearer $CRON_SECRET` header if `CRON_SECRET` is
set in Vercel):

```
curl -s "https://mission.srtagency.com/api/cron/followup-digest?dry=1" | jq '{policyScan, corpusScan}'
```

Expect both keys present. On a non-Thursday, `skipped: "weekday"`.

‼️ Neither is in `WATCHED_CRONS` and must not be added: `cron-health.ts` only watches crons that log
a success event **unconditionally**, and a weekday-gated passenger does nothing six days in seven.
