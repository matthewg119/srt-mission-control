# The onboarding brain: what it captures, what it decides, and what it still drops

Hand-written. Last measured against production **2026-09-18**, at commit `936b482`.

Read this with the two generated docs, which are the authority on the board itself and are
regenerated rather than edited:

- `docs/ONBOARDING-MAP.md` — every step: what reads it, what writes it, what it refuses on, and
  every outbound pull in the system. Generated by `scripts/_step-wiring.ts`.
- `docs/STEP-WIRING.md` — the 41 steps, their runners, verifiers and thread commands.
- `docs/ONBOARDING-MAP-MEASURED.md` — the same map measured against a real client
  (`bunx tsx --env-file=.env.local scripts/_step-wiring.ts --live`).

This file is the part no generator can produce: **why the data model is shaped the way it is, and
what is still being thrown away.**

## 1. The doctrine

Nine rules, in the order they get broken.

**1. An absence and a failure are different facts, and code must never collapse them.**
This is the rule everything else is a special case of. `Held<T>` in `lead-context.ts` encodes it in
the type: a value is `present`, `stale`, or `missing` with a `MissingBecause` of `never_asked`,
`asked_unanswered`, `blocked` or `unreadable`. `unreadable` means *we could not look*. Reporting it
as `missing` turns our own outage into a finding about the client.

**2. A `present` document whose derived field reads `missing` is a parser mismatch, not an
absence** (D14). Measured: SRT's awareness ladder was on file with five approved rungs while
`ctx.ladder` said missing, because the reader looked at `parsed.rungs` and the writer stored
`parsed.ladder.rungs`. Every card built on it would have asked for a ladder that existed.
Probe-enforced in `_probe-lead-context.ts`.

**3. Never cache a failure.** Every lane through `getOrFetch()` throws rather than returning a
null-shaped answer, because the door writes whatever `fetch()` returns and does not catch what it
throws. `RobotsUnreadable`, `SiteIntelUnusable`, `GeocodeUnavailable`, `MxUndetermined`,
`TranscriptFailed`, `SectionFailed`, `DocUnreadable`, `UnusableIdentity`, `UnusableProfile`. A
cached failure answers every later question with our own outage, for free, for the whole TTL.

**4. Cache facts, never measurements.** A page, a domain, an address, an MX record, a crawl, a
transcript, a document, a niche brief: all facts, all cacheable. An audit answer is a measurement
of what the engines said at a moment, and the whole product is the change between two of them.
Routing the fanout through the cache was reverted for exactly this (see §4).

**5. No number on a card that no process measured** (D9). `weekly-report.ts` tells the client in
writing that nothing counts leads (`ATTRIBUTION_NOT_WIRED`) rather than showing a plausible figure.
`suggestions.ts` says "page performance is NOT MEASURED" rather than guessing. The denominator
travels with the number: not "11 citations" but "11 of 441 across 15 audits".

**6. The tool proposes, a person confirms** (D7). Nothing publishes itself, nothing reruns itself
past the cursor, and a suggestion is a card with a reason, never an action.

**7. Every clip is declared.** A reader who cannot tell a whole document from most of one will
assume the missing part was never there. `final-prompt.ts` names every source it shortened, in the
file, at the end.

**8. One unknown column fails the WHOLE PostgREST select, and supabase-js RETURNS that error
rather than throwing it.** So a typo'd column name does not crash: it silently returns nothing and
every test above it passes. This bit this build (`client_docs.created_at` does not exist; the
column is `uploaded_at`) and the feature shipped doing nothing. **Read a new column in its own
select, and give any lane that reads a table a live probe.**

**9. A fetch() grep cannot find what the system buys.** It returns forty files and misses the
biggest spenders, because they build their URL in a variable. The census in `_step-wiring.ts` keys
on **credential-shaped env vars** instead: a provider you pay needs a key, so a key classified
neither as a paid provider nor as something else fails `--check` by name. There is no way to add a
paid provider to this repo quietly.

## 2. The workflows, and what to type

Every one of these is typed **inside a step's thread** in the client's own channel. The channel
top level is a wall by design: the only command there is `rerun <n>` / `rerun <n>-<m>`, and
everything else gets an ephemeral pointing you into a thread.

| Type this | Where | What it does |
|---|---|---|
| `gaps` | any client thread | What this step still needs, what each gap blocks, and the command that fills it |
| `prompts` | any client thread | The prompts that close **this step's** gaps, carrying what we already know |
| `suggest` | any client thread | What is worth doing next given everything we hold. Proposals only, each citing the rows it argued from |
| **`final prompt`** | any client thread | **One prompt for the whole lead**: everything on file, and everything still missing, across all 71 declared fields and every audience. Uploaded as a `.txt` |
| `rerun 12`, `rerun 18-21` | channel top level or a thread | Re-open a step or a range, then continue the board through the normal cascade |

`final prompt` is the one to understand, because it is the answer to "I want it to have all of the
context possible":

- It reads `ctx.gaps` **directly**, which is `evaluateDatasets` across every audience. The older
  `prompts` command reads `gapsFrom(ctx, stepKey)`, which is those same fields filtered through
  `STEP_NEEDS[stepKey]`. Even step 11, the widest, declares 56 of 71 and cannot see the audience
  fields or the offer fields written by a command.
- It carries **content, not presence**: the research already on file, the avatar sheet, the short
  offer, the sales letter, the beliefs as `B1: text`, the ladder and its anchor, keyword counts by
  stage, the domains the engines cited, who they named instead, the owner's own intake words, and
  the full text of every document ever dropped on the client.
- The avatar sheet and short offer come back **pre-filled** from what is stored, blank only where
  it is not, with every heading intact (`readTemplateDocument` refuses a paste matching fewer than
  half the headings).
- Research sections keep **the report's own numbers**. A subset renumbered from 1 files section
  12's answer under section 1, silently and permanently.
- Fields only Matthew can answer are listed under "NOT FOR YOU", rather than being asked for or
  hidden.
- It **refuses** rather than degrading: unreadable datasets mean what is missing is unknown, and an
  unconfirmed avatar means no prompt at all, because phrases filed under the wrong avatar land in
  `question_bank`, which is keyed by vertical, shared by every client in it, with no per-client key
  to unpick them by.

## 3. Where the data lives

**The read model.** `lead-context.ts` is the one place that assembles a lead, and it selects from
exactly one table (`client_datasets`); everything else comes through named readers. Eight slices:
`core`, `documents`, `keywords`, `pages`, `audits`, `research`, `history`, `gaps`. A slice that was
not requested reports `missing("unreadable", ...)`, never `missing("asked_unanswered")`, so "we did
not look" is never rendered as "it is not there".

**The gap model.** `dataset-spec.ts` declares **71 fields** across three datasets (avatar 42,
audience 7, offer 22), each with what fills it: a numbered research section, a heading of a pasted
framework document, a board command, the audit, or another field. `step-needs.ts` maps each of the
41 steps to the fields it needs and wants. That pair is what makes "ask only for what is missing"
mechanical rather than a promise.

**The document store.** `audience_documents` holds the six kinds (`deep_research`, `avatar_sheet`,
`short_offer`, `necessary_beliefs`, `sales_letter`, `awareness_ladder`) with full `content` and a
`parsed` shape. `client_docs` holds uploads: metadata, bytes in the `onboarding` bucket, and now
their extracted text through `doc-text.ts`.

**The shared corpus.** `question_bank` (keyed `vertical, avatar, normalized`, no `client_id`) and
`avatar_briefs` (keyed `vertical, avatar_slug`, with `first_client_id`) are deliberately shared: a
brief belongs to an avatar, not to whoever paid for it first.

**The cache.** `client_datasets`, one row per `(client_id, kind, cache_key)`. 12 of 23 outbound
pull sites go through it. **It is a cache and nothing more** — see §4.

## 4. What the cache is NOT, and why it matters

Corrected 2026-09-18 after auditing the lanes routed through it. The header of
`src/lib/data/dataset-cache.ts` used to claim both of these.

**It is not an archive.** The write is an upsert on `(client_id, kind, cache_key)`, and on conflict
Postgres **replaces** the row, payload included. A re-buy after an expiry overwrites the previous
answer. Any lane needing the old answer to survive the new one cannot get that here.

**`select kind, sum(cost_usd) from client_datasets group by 1` is not the spend.** It is the cost of
the *last* purchase of each distinct key, so a question bought five times counts once and a `force`
re-buy erases the receipt it was meant to add to.

Both are fixable with one append-only purchase table separate from the cache row. It is owed and it
needs a migration. **Until then, do not put that query on a card**: an undercount presented as a
total is worse than no number, which is rule 5.

This is also why two lanes were reverted after being written:

- **`run-prompts.ts` (the audit fanout).** Routed on the promise that the archive outlives the
  serving window. It does not. Worse, it broke two working things: `fanout_runs`/`fanout_queries`/
  `fanout_citations` are append-only evidence inserted per `runBatch`, so a watchdog re-kick inside
  the TTL appended the *cached* answer again as a second observation, inflating the only frequency
  count we have; and `search-research.ts` throws `UnusableProfile` so a rejected identity answer is
  bought and deliberately not kept, while the inner cache served that same rejected answer straight
  back, free, for the exact window a person re-runs in.
- **`extract-recommended.ts`.** Engine answers are freshly generated prose, so outside the fanout
  window the key differs every audit. Its only source of hits was the lane above.

## 5. What is still dropped on the floor

Measured 2026-09-18. This is the work list for "capture as much data as we need", ranked by what it
costs a real run. None of it is fixed.

### It changes a decision

1. **`MarketCenter.precision` is computed, documented as stored, and dropped by the caller.**
   `geocode.ts` returns it; `provision.ts` writes lat/lng/radius and not precision, and no column
   exists for it. A ZIP centroid sits 2 to 3 miles from the real address against a 10-mile radius,
   the centre is locked for the life of the tenant, and it is **what an exclusivity promise is
   measured against**. A ZIP-precision boundary is currently indistinguishable from an
   address-precision one.
2. **`zip_centroids` has two readers and no writer.** It is loaded by hand from a Census Gazetteer
   file. Unloaded, `geocodeZip` returns null, `resolveMarketCenter` treats that as "no centroid",
   and provisioning writes no market centre at all. `zipCentroidsLoaded()` exists to tell those
   apart and **has no callers** — the guard was written and never wired.
3. **`question_bank.frequency_score` is overwritten across runs, not raised.** The comment says a
   repeat harvest raises frequency; `mergePhrases` only merges within one run and the upsert
   replaces. A phrase seen in three harvests ends at the last run's count. `frequency_score` is what
   ranks a keyword, and the table is shared across the whole vertical for ever.

### It loses evidence

4. **`client_datasets.payload` has zero readers.** Everything the lanes archive is retrievable only
   by asking the byte-identical question again. `lead-context.ts` selects the metadata deliberately
   and not the payload.
5. **The whole fanout lane is write-only.** `fanout_runs`, `fanout_queries` and `fanout_citations`
   (6,060 rows) have no readers in `src/`. `market_mentions` is reachable only through the
   `market_competitors` view.
6. **`keyword_runs` / `keyword_decisions`** store the full "why did this keyword set come out this
   way" record, including the rejected candidates, which exist nowhere else. No readers.
7. **`list_pipeline_runs`** is opened at stage `pulling` and never advanced or read, so the funnel
   counts (pulled, survived MX, survived verification) are never recorded. That funnel is exactly
   the diagnostic wanted when a list comes out thin.
8. **`harvest_runs.error`** is written when the `question_bank` upsert fails and read by nothing,
   which is how the harvest silently reported "0 phrases from 0 pages" for months.
9. **`client_avatar_runs`**, **`hub_hits`**, **`page_dataset.research_prompt`**: single writer, zero
   readers.

### It breaks a promise made to a person

10. **`outbound_queue` has one writer and no readers.** A reply typed into a message thread is
    enqueued and never sent. Slack shows it as handled.
11. **The voice-note paste-back is promised and not implemented.** On a transcription failure the
    thread says "paste the transcript here and it will be used as if it had come from here". Nothing
    writes `client_docs.transcript` except the Whisper path.

### Smaller

12. **Per-client spend sees almost nothing.** 11 of 12 routed lanes pass `clientId: null`, which is
    correct on the merits (a page, a domain, an MX record are facts about the world), but it means
    `lead-context`'s research slice and `spendSoFar(clientId)` only ever see `storage.doc_text` rows
    at $0.00. The row does not know who caused the purchase.
13. **`intel-brief`'s cache key omits `buyer_persona`**, which reaches the prompt and changes the
    answer. Two reports in one trade with different personas share one cached brief.
14. **The map's "through the door" column is grepped at file level**, not per function, so it would
    read "yes" for an unrouted function in a file where a different one got routed. Correct today,
    will eventually lie.

## 6. Suggestions: what exists and what does not

`suggest` (shipped) argues from six branches, each carrying a `basis` naming the rows it counted:
keywords approved but unroled, the anchored rung versus where the keywords actually sit, the board
cursor against the thread, the blocking gap with the longest tail, one audience with live pages,
and a permanent D9 guard that says page performance is **not measured** rather than implying it is
fine.

What is owed is the half that leaves the board (C13c): proposing a **new avatar**, a **new offer**
or **new angles**. The tables already exist and the model is settled — `client_audiences` →
`avatar_briefs` / `client_offers` → `audience_documents` → `client_keywords` → `page_plan` →
`client_pages` — so a suggestion to build a new avatar is a proposal to insert a `client_audiences`
row and walk the framework again for it. It is blocked on the same thing every honest suggestion is
blocked on: **live page performance does not exist yet**, and D9 forbids arguing from a number
nothing measured.
