## 3A. The universal set becomes vertical-aware, and stays frozen

In `src/lib/clients/question-sets.ts`:

> **`UNIVERSAL_V1_MED_SPA` and `freezeUniversalV1()` ARE UNTOUCHED.** That file's header pins
> those twenty to the shipped 20 Questions PDF, character for character, because *"A2 section
> 4: the tracked set must be the questions the public actually received, because Beat 11 says
> so on camera."* The med spa lane keeps working exactly as it does today. You are adding a
> branch for everybody else, not editing the med spa one.

- New `universalSetFor(clientId)`. Vertical `med_spa` returns the twenty verbatim. Any other
  vertical derives twenty from **that client's own** `audit_reports.prompts` and **freezes
  them as `universal_v1@{vertical}` in `question_set_versions`, once.**

  > **Freeze-once is the whole point.** `audit_reports.prompts` is REGENERATED by every audit
  > run (`findings.ts` spells out the hazard), so quoting it live would let a later scan
  > silently rewrite the questions in a report already sent to a client. The Day-0 tracked
  > set has to be frozen. `freezeUniversalV1`'s upsert is already `ignoreDuplicates`, so
  > follow that shape and you inherit "never edited in place" for free.

- **Substitutions stop guessing.** `MATERIALIZATION_FALLBACKS` (`melasma`, `Morpheus8`) are a
  fact about the med spa twenty and apply only to them. Outside `med_spa`, a question whose
  placeholder cannot be filled from `services` or `ideal_patient` is **DROPPED, not
  materialized with a wrong noun.** A dropped question is honest; "the best med spa for
  Chatgpt ads" is not.
- The fidelity footer already reports which fallbacks were used. Extend it to say which
  questions were dropped and why.
- **`competitorIntake1` falls back to the top SELECTED competitor** from
  `competitor_candidates` rather than to whatever was typed at intake. A client typing `"a"`
  stays on the shortlist, because *"a client naming businesses no engine has heard of is
  itself a finding"*, but it is not a question we put to an engine.
- **Questions 1 and 2 come from intake** where intake has them: the primary service and the
  city. `substitutionsFor` already reads `services.primary_service` and
  `ideal_patient.highest_margin`; the gap is that nothing distinguishes a real intake value
  from a fallback. The call sheet and the PDF label each question **`from intake`** or
  **`from the universal set`**, so the client corrects the right ones on the call.
- `substitutionsFor` is **one mapping with three consumers** (the call sheet, the custom
  question set, the page candidates). That comment is there because three copies is how the
  call sheet ends up printing a substituted question that differs from the one being tracked.
  Keep it single.

about the funnel, online presence, GBP profile, capture DNS and all the rest, we cant capture

would ask based on the report we did and I will select the ones I like."*

New `src/lib/clients/artifacts/call-questions.ts`, filed against `call_held`, generated when
`call_sheet` completes. Register it in `artifacts/registry.ts`.

**Ordered by CLOSER, which is already this repo's spine** (`call-coach/suggest/route.ts`,
`STATIC_RULES`: *"CLOSER is the spine and it runs in order"*):

| Section | What its questions are for |
|---|---|
| **C** larify | why they are on this call at all |
| **L** abel | name the problem in their words |
| **O** verview | their previous pain, what they already tried and what it cost |
| **S** ell | the dream outcome |
| **E** xplain | their concerns, answered before they raise them |
| **R** einforce | show what we already did, then ask for the card |

Then a hard divider and a separate section, on its own page:

> **AFTER THE CARD.** Funnel, online presence, GBP manager, Search Console, Analytics, DNS,
> booking software, review workflow. **None of these is asked before the commitment.**

- **33 questions, each with a checkbox** so he picks. Use `correctionBox` / the existing
  `@/lib/pdf/kit` primitives; do not invent a second PDF style.
- **The facts are code, the questions are the model's.** Same split `buildCoachNotes()`
  makes, and for the same reason: the score, the absent organic prompts, the competitors
  named instead, the presence sweep findings, the review audit gaps and the site intel are
  assembled BY HAND and handed to the model as **the only numbers that exist**. It writes
  questions from them and invents nothing. A hallucinated figure in a document read aloud on
  a sales call is not one bad line, it is the whole call.
- Validation: reuse `spokenPromises` and `noDashes` from the existing guards, plus a 25-word
  cap per question. A price, a guarantee or a promise of customers or revenue fails the
  generation into `callClaudeJSON`'s correction retry.
- **`describeInvalid` must cover its WHOLE validator.** `booking-script.ts` records exactly
  what happens when it does not: it described only the shape, so when the word cap was what
  failed the correction retry got a rejection with no reason and answered *"I cannot fix the
  error without knowing what the rejection reason was"* - not JSON, so the parse threw, on
  every run. Quote the offending lines back.
- `MAX_TOKENS` must stay **under 8000**, or `callClaudeJSON`'s truncation retry is silently
  disabled and a cut-off response fails as an unparseable-JSON error whose message says
  nothing about length.

## 3C. Payment unlocks step 21

Matthew: *"After we receive the payment it unlocks step 21 for GBP manager search console
etc."* His chosen mechanism: **he ticks it, with a note.** No Stripe.

Your migration adds to `clients`:

```sql
alter table public.clients
  add column if not exists payment_recorded_at timestamptz,
  add column if not exists payment_recorded_by text,
  add column if not exists payment_terms       text,
  add column if not exists payment_note        text;
```

`billing_status` already exists and reads `'pilot'` on the live client.

- New `POST /api/clients/[id]/payment` and `src/components/clients/payment-form.tsx`, panel
  `id="payment"`, placed **below** the existing `id="review-handover"` block.
  What was agreed, card on file yes or no, the date, who recorded it.
- `stepPrecondition` gains an `access_granted` branch refusing while nothing is recorded. The
  refusal **states the reason, not just the rule**: technical access is collected after the
  commitment, because a client who has not committed does not hand over their Google account,
  and asking early is how a call ends without either.
- `access_granted`'s card says the same thing above its click paths. That card is good and
  its click paths are correct; you are adding a gate above it, not rewriting it.

> **THIS IS AN ASSERTION THE BOARD RECORDS, NOT EVIDENCE OF A CHARGE**, and no artifact may
> blur the two. It is the same distinction `day_0_source` draws between `photograph_2` (a
> real archived run wrote it) and `manual_step` (a human ticked a box, which is an assertion
> that the thing happened, not evidence of it). Write it as "payment recorded by {who} on
> {date}", never as "payment received".
