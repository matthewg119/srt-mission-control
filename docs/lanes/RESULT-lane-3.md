## 3B · Step 20 hands over 33 closing questions

New `src/lib/clients/artifacts/call-questions.ts`, generated by the existing `call_sheet` runner in
`artifacts/registry.ts`, filed against `call_held`.

- **33 questions, checkboxed, in CLOSER order** — Clarify, Label, Overview, Sell, Explain,
  Reinforce. The same spine `call-coach/suggest/route.ts` runs on, so the document and the live
  coach cannot be at different stages of the same call.
- **The facts are code and the questions are the model's.** `buildQuestionFacts()` assembles the
  score, the organic questions the business is absent from, who was named instead with each one's
  own count, the core-six presence, the review gaps and the site intelligence. `factsBlock()` hands
  them over as "the only facts that exist" and states absences out loud (`SCORE: NONE. Do not cite
  a score`), because absent beats forbidden.
- **Absent prompts come from `audit_runs.prompt`, never `audit_reports.prompts`** — the same rule
  `findings.ts` states, for the same reason.
- **`questionProblems()` is the whole validator and `describeInvalid` is the whole of it**, quoting
  the offending line back by word count. Six branches: shape, count, empty section, the 25 word cap,
  `spokenPromises()`, and section keys. `booking-script.ts`'s failure is why.
- `maxTokens: 4000`, under `MAX_RETRY_TOKENS`, so the truncation retry is live.
- **A hard divider, then `AFTER THE CARD` on its own page**, built in CODE from what the record
  already holds: the real registrar and click path, the seeded CNAME values, the booking software,
  the named review person. It refuses to guess: an unseeded CNAME prints "not seeded yet" rather
  than `HUB_CNAME_TARGET`'s default, which is measured wrong for this project.

### The one deliberate deviation from the brief

> **It does not call `deliverArtifact`.** `deliverArtifact` → `anchorTsFor` → `postStepAnchor`
> **creates** the step's Slack anchor. This runs when step 18 completes, so posting the file would
> put step 20's top-level message in the channel while step 18 is still the cursor — precisely the
> leak `reachableCursor`'s doc block names, and `hub_preview` is the example it gives.
>
> Instead it stores the bytes through `storeGeneratedDoc({ stepKey: "call_held" })` and writes
> `call_held.output_ref` itself. **Step 20's card links it** through the `outputRefsFor` / `docLink`
> path every other card already uses, the moment that step legitimately appears. Matthew's answer
> when this was put to him: store now, link on step 20's card.

`AUTO_RUNNERS` gains **no key**. Its shape is unchanged, `unreachableAutoSteps()` is untouched, and
the test asserting the unreachable set is empty still passes. A failure in the questions half is

**Run this. Nothing in 3C works until you do.**

```sql
alter table public.clients
  add column if not exists payment_recorded_at timestamptz,
  add column if not exists payment_recorded_by text,
  add column if not exists payment_terms       text,
  add column if not exists payment_note        text;

comment on column public.clients.payment_recorded_at is
  'When a human RECORDED that payment is arranged. An assertion, not a receipt: nothing here '
  'talks to a payment processor. Same doctrine as day_0_source = manual_step. Never render this '
  'as "payment received".';

comment on column public.clients.payment_recorded_by is
  'Who made the assertion, from the signed-in session. Printed beside the date everywhere it is '
  'read, because an unattributed assertion is indistinguishable from an observation.';

comment on column public.clients.payment_terms is
  'What was agreed, in words. Required to record: a payment with no stated terms is a tick, and '
  'a tick is what this design exists to refuse.';

comment on column public.clients.payment_note is
  'Optional. Whether a card is on file, what is still outstanding, anything the next person '
  'needs. Free text.';
```

`'pilot'` on the live client.

New `src/lib/clients/payment.ts` — `paymentRecorded()`, `paymentLine()`, `ACCESS_GATE_REASON`,
`ACCESS_GATE_TODO`. A separate module because the gate is needed in two shared files and two copies
of the read is how the two answers start disagreeing.

**The gate is in the verifier, and that is the load-bearing part.** `stepPrecondition` is called
from `api/slack/actions/route.ts` and nowhere else; the client board's checkbox posts straight to
`api/clients/[id]/delivery-step`, which calls `setDeliveryStep`, which runs `verifyStep` **before
the row write**. A gate living only in `stepPrecondition` is bypassed by the board. Both carry the
refusal now, reading the same module.

- No payment recorded → `not_yet`, so the step keeps its `[Re-check]`. A read failure → `broken`,
  with the fix line naming this migration.
- The refusal **states the reason, not the rule**: technical access is collected after the
  commitment, because a client who has not committed does not hand over their Google account, and
  asking early is how a call ends with neither.
- `access_granted`'s three click paths are **verbatim unchanged**. A gate line was added above them.

`src/app/dashboard/clients/[id]/payment-form.tsx`, `id="payment"`, below `id="review-handover"`.
